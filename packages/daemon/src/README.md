# Daemon Source

The LobsterFarm daemon process. Manages entities, spawns Claude Code agent sessions, routes Discord messages, and exposes an HTTP API for the CLI and Commander to interact with. Runs as a macOS launchd service.

## Files

- `index.ts` -- Entrypoint. Wires up all subsystems (registry, sessions, queue, Discord, Commander, pool) and handles graceful shutdown.
- `config.ts` -- Loads and validates the global `~/.lobsterfarm/config.yaml` file.
- `registry.ts` -- `EntityRegistry` class. Scans `~/.lobsterfarm/entities/` on startup, validates each entity's `config.yaml`, and provides lookup by ID.
- `session.ts` -- `ClaudeSessionManager`. Spawns Claude Code as child processes with the correct agent, model, DNA, permissions, and entity context. Tracks active sessions, captures output, emits lifecycle events.
- `queue.ts` -- `TaskQueue`. Priority-ordered queue that feeds sessions to the session manager, respecting the configured concurrency limit. Processes next task when a slot opens.
- `server.ts` -- HTTP API server. Routes for status, entities, tasks, pool management, entity scaffolding, reload, webhook endpoints, the per-PR review-lease API (`GET review-state`, `POST`/`DELETE review-lease`), and the staging-gate promotion endpoint (`POST /pr/:owner/:repo/:num/staging-promotion`, #104). `POST /hooks/stop` additionally records the calling session's `working_dir` as worktree occupancy in the `WorktreeLeaseStore` (#105) -- this is the daemon's only inbound signal about agents it did not spawn, so the auto-fix gate is blind without it. The promotion route owns the lease lifecycle -- it acquires `daemon-staging` (409 if a review/merge already holds the PR), calls `run_staging_promotion`, and releases in a `finally` so a refusal can't strand the lease for its full TTL.
- `router.ts` -- Discord message router. Deterministic rules: channel-type routing (alerts, general), keyword-based intent classification. Legacy `!lf` prefix parsing retained for test coverage.
- `discord.ts` -- `DiscordBot` class. Connects to Discord via discord.js, builds a channel-to-entity index from entity configs, handles incoming messages via the router, sends messages as webhooks for agent identity, and scaffolds new entity Discord categories/channels.
- `commander-process.ts` -- `CommanderProcess`. Manages Pat (the Commander) as a persistent Claude Code session inside a tmux session with the Discord channel plugin. Health-checks every 10s (tmux death + MCP plugin-liveness deafness, issue #77), auto-restarts with exponential backoff, and resumes the persisted session on recovery. The deafness probe is gated by `LIVENESS_WARMUP_MS` off `last_started_at` (#111) -- the same warm-up the pool's call sites got in #108, so no reading is taken while a freshly respawned pane is still showing boot banners.
- `pool.ts` -- `BotPool`. Manages a pool of Discord bot accounts (pool-0 through pool-N) for assigning to channels. Handles assignment, release, LRU eviction, parking (session preservation), nickname setting, pre-assignment of planners to entity #general channels, and the MCP plugin-liveness deafness probe (issue #73). A deaf verdict auto-recycles the channel release-to-fresh — the same release + assign an operator does by hand — with a per-channel loop guard (#106); `heal_post_restart` is the one-shot post-restart pass that recycles resumed sessions showing zero turn evidence since their resume nudge (the 08-01→08-04 "alive but receiving nothing" incident class), with an aggregate operator alert.
- `gateway-watchdog.ts` -- `GatewayWatchdog` (#107). Heartbeat-recency liveness for the daemon's single Discord gateway: samples shard heartbeat-ack timestamps (`shard.lastPingTimestamp`, discord.js v14) on a timer and, on sustained silence (default 3 missed heartbeat intervals ≈ 2 min) with no discord.js reconnect in flight, destroys and re-logs-in the client. Sentry event fires FIRST (Discord itself may be the sick component), then a best-effort Discord alert. Not broker-flag-gated — protects today's gateway too. Probe/recycle/clock all injectable; `DiscordBot` hosts the probe and the recycle.
- `plugin-liveness.ts` -- Shared MCP plugin-liveness probe logic (issues #73, #77). `evaluate_plugin_liveness` is a pure verdict function comparing inbound/processing timestamps against tmux pane-idle state to detect a "deaf but alive" session; `is_tmux_session_idle` reads the pane. Also owns `PLUGIN_DEAF_THRESHOLD_MS` (grace window before idleness counts as deafness) and `LIVENESS_WARMUP_MS` (how long after a respawn before *any* reading is trusted); all three probe call sites -- the pool's two and the commander's -- apply the warm-up gate, so their decisions stay provably identical (#106, #108, #111). Consumed by both `pool.ts` and `commander-process.ts` (re-exported from `pool.ts` for existing importers).
- `actions.ts` -- Side-effect functions: git worktree create/cleanup, GitHub PR create/merge via `gh`, test runner, and Discord notification dispatch.
- `worktree-cleanup.ts` -- Worktree removal: post-merge cleanup (`cleanup_after_merge`) and the hourly stale sweep (`sweep_stale_worktrees`). Four independent gates stand between a worktree and deletion, and all four fail toward *keeping* it. (1) **Live-agent shield** (#110): a worktree root holding `.lf-agent-active` is never removed, by any path, with no alert and no tmux relocation -- see "Live-agent shield" below. (2) **Unstarted-branch classifier** (#110): a branch whose tip sits on the trunk's first-parent history has produced no commits of its own, so it is unstarted rather than finished; an unresolvable trunk abandons the whole repo. (3) **#27/#30 safety preconditions**: no uncommitted changes, no untracked files, no commits unreachable from any remote ref -- a failure here skips the removal and posts an action-required alert. (4) **Branch identity**: `remove_worktree` is only ever called with the branch actually checked out in the directory being deleted, because #30's unpushed check is evaluated against the branch it is given. `.claude/worktrees/` directories are therefore matched on the branch git reports for the directory itself -- never on their name (those are the Claude Code harness's `EnterWorktree` worktrees, named randomly `agent-<hex8>` with no relation to any branch) and only once the directory is confirmed to be the root of a working tree belonging to *this* repo, because `git symbolic-ref` answers for whatever repository encloses a path. `remove_worktree` enforces the invariant itself rather than trusting callers. Known limitation: fast-forward-merged and squash-merged worktrees are never reclaimed automatically; both are documented in the source, and the reclaim path is issue #129.
- `review-utils.ts` -- Utility functions for PR review feedback: fetch review comments from GitHub and build fix prompts for the auto-fix loop.
- `hooks.ts` -- Post-session hooks. Extracts session learnings via Haiku and appends them to daily logs. Also manages the global learnings file. The Haiku call goes through `claude-cli.ts`; extraction is best-effort, so a broken invocation here fails silently and only shows up as stale memory (issue #79).
- `claude-cli.ts` -- The daemon's **only** entry point for headless `claude -p` invocations. `run_claude_print` spawns the CLI with the prompt on stdin and closes stdin immediately. This is mandatory, not stylistic: `promisify(execFile)` never closes the child's stdin, and `claude -p` blocks on stdin even when the prompt is passed as an argv argument -- it warns `no stdin data received in 3s` and burns ~3s of the caller's budget (issue #79, which cost us the heartbeat backstop and then ~40% of all memory extractions). Any new `claude -p` call site MUST route through here; never `promisify(execFile)`.
- `models.ts` -- Maps abstract model tiers (opus/sonnet/haiku + think level) to Claude CLI flags.
- `persistence.ts` -- JSON file persistence for PR review state and pool state. Saves to and loads from `~/.lobsterfarm/state/`. **All seven** state writers go through one exported `write_json_atomic` helper (write to a `<file>.<8 hex>.tmp` sibling, then `rename`), which removes the temp file on every failure path -- a failing `rename` used to orphan it permanently, which is how live state accumulated four `pr-reviews.json.*.tmp` files from four different dates. The seven are the four savers here plus `alert-router.ts` (`active-incidents.json`), `sentry-triage.ts` (`sentry-triages.json`) and `broker/queue.ts` (`broker-queue.json`) -- the last is the highest-frequency writer in the daemon and its caller swallows persist failures, so a leak there accumulated silently. Their basenames are declared here (`ATOMIC_STATE_FILES`) and imported by those modules, because `STATE_TEMP_PATTERN` is **anchored** to that list: the sweep deletes, so "we only ever remove our own files" is a property of the regex rather than of who currently writes to the directory. A new state writer must be registered in that list or its orphans are never swept. `sweep_stale_state_temps` covers what in-process cleanup structurally cannot (a daemon killed *between* write and rename) and is awaited once at startup from `index.ts`, before any subsystem writes state. `load_pr_reviews` sanitizes on load (#102 Gap 3) -- malformed / mismatched / unknown-entity keys are dropped, logged, and the file rewritten clean (self-healing against leaks like a bogus `lobster-farm:6010`). Under `NODE_ENV=test`, both the writes and the sweep's **deletes** refuse to proceed when the state root resolves to the real `~/.lobsterfarm` (forces tests to sandbox `paths.lobsterfarm_dir`).
- `pid.ts` -- PID file management. Write, read, remove, and check if the daemon is already running.
- `singleton.ts` -- Singleton port guard (issue #97). `acquire_port` binds `:7749` up-front (before Discord/pool/commander start) and returns the listening server for `start_server` to reuse; on `EADDRINUSE` it logs a single line and exits 0 (deliberate stand-aside) instead of crash-looping. `classify_listen_error` is the pure decision function (unit-tested).
- `log-rotation.ts` -- Size-based log rotation (issue #97). `rotate_log_if_needed` renames `daemon.log` to `daemon.log.1` on startup when it exceeds the cap (25 MB default), because launchd never rotates its `StandardOutPath`. Best-effort; keeps a single backup to bound disk usage.
- `pr-cron.ts` -- `PRReviewCron`. Polls entity repos for open PRs, spawns headless reviewer sessions, and routes outcomes (approve/merge, fix, escalate). Acquires a `ReviewLeaseStore` lease (`daemon-cron`) before spawning so it never collides with the webhook or manual review paths, and **holds that lease through the merge** — every merge site is gated by `assert_can_merge` (#102), so an auto-merge can't fire while another review is in flight. `should_skip_pr` counts only genuine reviewer feedback (formal reviews + the reviewer identity's `**Verdict:` comments), so a PR author's own comment after a push never suppresses re-review (#102 Gap 2). Before spawning an auto-fix builder it also claims the PR's **linked** worktree from the `WorktreeLeaseStore` (#105) and **defers** rather than spawning a second editor into a tree another live agent holds; the deferred fix is persisted as `fix_deferred_at` and drained by `retry_deferred_fixes` on a later tick (the marker is required because `reviewed_at` makes `check_repo` skip the PR, so without it the owed fix would be silently dropped). Branches living in the repo's *main* working tree are deliberately not leased -- that root is a shared workspace where a reviewer and a fixer legitimately coexist, and leasing it would turn a race into a pipeline-wide outage.
- `webhook-handler.ts` -- GitHub webhook handler. Receives PR events, verifies signatures, maps repos to entities, and spawns reviewer/fixer sessions. Acquires a review lease (`daemon-webhook`) before spawning and holds it through post-review routing; every merge site (v1 auto-merge + v2 `run_merge_gate`) is gated by `assert_can_merge` (#102). The lease is released only after routing completes, before any SHA-move requeue.
- `review-lease.ts` -- `ReviewLeaseStore`. In-memory per-PR review mutex (issue #60). A lease (key `owner/repo#num`) is acquired by one of four holders -- `daemon-cron`, `daemon-webhook`, `tidus-manual`, `daemon-staging` -- before a reviewer spawns, so two reviewers never run on the same PR. The lease also **gates the merge, not just the spawn** (#102): `holds()` + the `assert_can_merge()` helper let every merge call site confirm the caller still owns the live lease before merging (fail-open when the store is absent). Lazy TTL expiry (20 min default, tunable via `pr_cron.review_lease_ttl_ms`); no disk persistence, no background sweeper. Two guards, deliberately different: `is_lease_holder` accepts any holder, while `is_agent_acquirable_holder` -- the one the HTTP routes use -- rejects `daemon-staging` (#104), because an agent able to take that holder could stall every promotion on a 409, or release the lease out from under a promotion in flight.
- `worktree-lease.ts` -- `WorktreeLeaseStore`. In-memory per-worktree single-owner mutex (issue #105), keyed by canonical worktree path (symlinks collapsed, so `~/.lobsterfarm/src` and its `entities/.../repos/...` alias can't both be leased). Two lease kinds: **explicit** (`daemon-cron`, taken before a spawn, released at session end) and **observed** (`agent-observed`, inferred from the Stop hook). The observed half is what sees agents the daemon did *not* spawn -- a human's CLI session, a pool bot, a commander-dispatched builder -- which is the case that caused the PR #103 clobber. Four independent release paths so a hold can never become an outage: explicit release, pid-based crash reaping, TTL (60 min explicit / 15 min observed, tunable via `pr_cron.worktree_lease_ttl_ms` and `pr_cron.worktree_observed_ttl_ms`), and daemon restart. Stand down with `pr_cron.worktree_lease_enabled: false`, which constructs no store at all -- every call site is null-guarded, so off is the pre-#105 code path. The store is built by `make_worktree_lease_store(config)` rather than inline in `index.ts`, because `index.ts` ends in a top-level `void main()` and so is unreachable from any test -- which is how #105 first shipped as dead code. `worktree-wiring.test.ts` covers the factory and asserts structurally that `index.ts` still calls it.

  **Two accepted residuals, both deliberate -- do not read the gate as total.** (1) The repo's **main working tree is never leased**: `touch_observed` fires for every session on the machine and every daemon spawn passes the repo root as cwd, so a root lease would be renewed continuously and would block the fixer path near-permanently -- a standing outage in place of an occasional race. The cost is that a branch checked out *at the root* is ungated, and `git checkout` succeeds there because the branch is already current. (2) The gate is **single-sided**: pr-cron claims before spawning, but the webhook/check-suite fixer paths do not (#121). Because the observed half is global, pr-cron is protected *against* those paths; only the reverse is open.
- `staging-promotion.ts` -- `run_staging_promotion` (#104). Daemon-owned `staging → main` promotion for repos using the staging gate, closing the last exception to #102's single-chokepoint guarantee (`pr-review-merge` SOP step 4a.next previously told an agent to run the git commands by hand). Two gates, in order, both before any git side effect: a **human sign-off** naming the configured human (`config.user.name`), then `assert_can_merge` on the `daemon-staging` lease. The lease is asserted *inside* this function rather than trusted from the caller, so a future call site that forgets to acquire is refused instead of silently promoting. Fast-forward-only is enforced twice -- a local ancestry check yielding a precise `diverged` outcome to escalate on, plus a plain non-forced push the remote rejects on a non-fast-forward. Never mutates a working tree (no `checkout`); all git calls use `git -C <path>`. Note on fail-direction: the lease check **fails open** when no store exists (consistent with `assert_can_merge` everywhere), but the sign-off check **fails closed** -- an empty approver list permits nobody, never everybody. Git ops are behind an injectable deps seam.
  - **The sign-off is an intent relay, not authentication.** It proves a human decision was explicitly relayed; it does not prove the relay came from Hunter. The daemon trusts its localhost callers, as every other route here does.
  - **Still agent-side:** the PR → `staging` merge (SOP 4a.3) has no daemon equivalent and is *not* behind the chokepoint. It is the more race-prone of the two staging merges, since it fires right after the Approved verdict. See the warning in SOP step 4a.3.

## Live-agent shield

To pin a worktree against the hourly sweep, create `.lf-agent-active` in its root:

```
touch /path/to/worktree/.lf-agent-active
```

The sweep then skips it unconditionally -- no removal, no branch delete, no tmux `cd`, and no alert (it is deliberately held, not stuck). Delete the file to release it. There is no grace period and no expiry: a marked worktree stays until the marker goes, so a marker left behind by a crashed agent pins its worktree indefinitely (issue #129 covers adoption, visibility, and expiry).

The marker is honored regardless of git ignore state -- it is checked with `stat`, not `git status`. **Do not commit it**: it is per-worktree, transient state.

## Key Concepts

- **Session spawning**: The daemon never runs Claude Code interactively. It spawns headless sessions with `--output-format stream-json` and pipes the prompt via stdin.
- **Bot pool**: Discord bot accounts are a limited resource. The pool assigns them to channels on demand, evicts via LRU when full, and parks sessions for later resume.
- **Commander (Pat)**: The only agent that runs persistently. Lives in a tmux session, connected to Discord via the channel plugin, operating at the platform level rather than entity level.
- **PR review loop**: PRs are reviewed by spawning headless reviewer sessions. If changes are requested, a builder is spawned to fix. GitHub issues and PRs are the source of truth.
